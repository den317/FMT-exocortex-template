# [DP.SC.NNN] Синхронизация РП с внешним трекером

## Обещание

Сервис поддерживает два детерминированных маршрута. После полной локальной
регистрации РП он создаёт или находит ровно одну GitHub issue с тем же WP-ID.
Для явно разрешённых входящих репозиториев сервис также регистрирует каждую
post-cutover GitHub issue как ровно один минимальный РП. Прямой API downstream-
трекера не используется.

## Контракт

| Поле | Значение |
|------|----------|
| Триггер | успешное создание РП, начало ритуала или явный запуск проверки |
| Входы | WP context либо GitHub issue; allowlist и adoption cutover |
| Выходы | каноническая связь в context frontmatter; отчёт проверки |
| Время отклика | локальная проверка ≤1с без сети; GitHub create/check ≤15с |
| Инвариант | одна WP ↔ одна GitHub issue; auto-adopt никогда не создаёт issue |
| Режим отказа | конфликт/сеть дают явный статус; adoption откатывает частичный локальный WP |

## Маршрутизация

| Результат | Owner-repository |
|-----------|------------------|
| личные РП, планы и стратегия | `DS-strategy` |
| настройка конкретной установки | `IWE` |
| изменение платформы для всех установок | `FMT-exocortex-template` |

Неоднозначный или многорепозиторный результат не маршрутизируется
автоматически. Пилот или агент обязан передать один owner-repository.

## Сценарии использования

### 1. Личный рабочий продукт

`/wp-new` полностью регистрирует РП в `DS-strategy`, после чего сервис создаёт
`WP-N Название` в GitHub Issues `DS-strategy`. Повторный запуск возвращает URL
существующей issue.

### 2. Настройка установки

РП с owner-repository `IWE` создаёт issue только в `IWE`. Linear отражает её
штатной интеграцией; сервис не обращается к Linear.

### 3. Платформенное изменение

РП с owner-repository `FMT-exocortex-template` создаёт issue в fork владельца.
Описание содержит только минимальный публично допустимый контекст без личных
данных из `DS-strategy`.

### 4. Внешняя работа появилась первой

`reconcile` читает issues во всех состояниях только из adoption allowlist.
Issue до cutover не меняются. Для новой несвязанной issue вызывается `adopt`:
заголовок сохраняется без переформулирования, ссылка записывается штатными
полями, WeekPlan не меняется и новая GitHub issue не создаётся.

## Проверка связи

Режим `check` классифицирует наблюдаемые состояния:

- `OK` — одна открытая issue для активного РП;
- `MISSING` — issue отсутствует;
- `DUPLICATE` — найдено больше одной issue с WP-ID;
- `STALE` — РП закрыт, issue открыта, или активный РП связан с закрытой issue;
- `WRONG_REPO` — сохранённая issue принадлежит не owner-repository;
- `UNAVAILABLE` — GitHub недоступен; состояние Linear не заявляется как успешное.
- `ALREADY_LINKED` — входящая issue уже имеет ровно один WP;
- `CONFLICT` — одна входящая issue указана более чем в одном WP.

## Критерии приёмки

1. Повторное создание идемпотентно.
2. Конфликт не исправляется угадыванием.
3. Недоступность GitHub не откатывает локальный РП.
4. В context file сохраняется URL issue.
5. Canary GitHub ↔ Linear пройден для `DS-strategy`, `IWE` и
   `FMT-exocortex-template`.
6. Reconcile учитывает open и closed issues после cutover и не меняет WeekPlan.
7. Повторный reconcile не создаёт второй WP или новую GitHub issue.
8. Закрытая связанная GitHub issue детерминированно закрывает и архивирует WP без вопросов; рефлексивное обогащение выполняется позже и не блокирует lifecycle.
