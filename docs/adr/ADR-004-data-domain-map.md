# ADR-004: Карта доменов данных IWE

**Статус:** Принято (методология, рекомендуемая структура)
**Дата:** 2026-08-16
**Контекст:** РП-526 (Новая структура IWE), Ф2/Ф4, пир-сессия Claude+Kimi `2026-08-16-21-wp526-f4-template-transfer`

---

## Контекст

Структура репозиториев внутри одного экземпляра IWE (шаблон + пользовательские репо) складывается стихийно, если её не спроектировать заранее: типы данных пользователя (профиль, события, знания, сессионные диалоги и т.д.) смешиваются с кодом, планами и машинными артефактами в одном месте, что со временем бьёт по скорости работы инструментов, безопасности (карантин персональных данных держится на конвенции, а не на структуре) и по возможности обновлять шаблон без ручного слияния конфликтов.

Эта карта — результат отдельного разбора (РП-526), прошедшего внутреннюю архитектурную оценку (профиль ЭМОГССБ, критические характеристики — Безопасность и Эволюционируемость — без вето). Она фиксирует **рекомендуемую** структуру для нового пользователя IWE, а не обязывает существующих пользователей к миграции: у каждого пользователя может быть свой путь и темп приведения своей структуры к этой карте (или отклонение от неё по собственному решению).

**Смежный документ:** [DATA-RESIDENCY.md](../DATA-RESIDENCY.md) — более ранний и более простой предшественник (WP-475, 10.07.2026), §3 которого содержит текстовую таблицу 4 типов данных (2.1-2.4) без темпа изменения, чувствительности и правил потоков. Этот ADR не заменяет и не редактирует тот документ (он держит свою собственную, уже закрытую фазовую границу) — он вводит более полную, машиночитаемую карту рядом, с явной перекрёстной ссылкой в одну сторону (отсюда → туда).

## Решение

### Карта доменов (тип × темп)

Ось темпа: **hot** (правится ежедневно/ежесессионно) · **warm** (по фазам работы, неделями) · **cold** (архив, редко или никогда).

| Домен | Темп | Роль хранилища | Обоснование |
|---|---|---|---|
| 2.1 факты о носителе (профиль, характеристики) | warm | `personal-declarative` (git) + платформенная runtime-проекция | декларация и вычисляемое значение разделены по роли, не смешиваются |
| 2.2 события/телеметрия | hot | `personal-data` (git, append-only) + платформенная БД | активный поток записи — источник наибольшего роста истории и конфликтов при смешении с планированием |
| 2.3 знания/captures | warm | вне-git память + промотированное знание (Pack) | сырые заметки и оформленное знание — разные стадии жизненного цикла, разные дома |
| 2.4 неформализуемое | — | явный карантин «не размещать» | не структура, а маркер — решение принимается отдельно, эта карта только на него ссылается |
| 2.5 диалоговые артефакты (сессионные транскрипты) | warm→cold | `governance-personal` (git, `sessions/`) | не факт, не телеметрия и не готовое знание — сырьё для последующего извлечения знания; со временем архивируется, не удаляется |
| 2.6 карантин-диалоги (подмножество 2.5) | — | тот же дом, что 2.5, с отдельным access-контролем | данные о третьих лицах внутри диалогов требуют более строгого режима доступа, чем остальной домен 2.5 |
| runtime/state | hot | вне git (например `.iwe-runtime/`) | декларируется явно как класс дома, не переносится в git-историю |
| код/скрипты — рабочая копия | hot | рабочий репозиторий пользователя | правится в ходе любой сессии, где нужен фикс инструмента |
| код/скрипты — промотированная копия | warm | `FMT-exocortex-template/scripts/` | обновляется по решению о промоции, не ежедневно — та же логика, другая стадия |
| планы/рабочие контексты | hot | `governance-personal`, без потока телеметрии и без единого растущего файла знаний внутри | смешение планирования с активным потоком записи — источник конфликтов при закрытии сессий |

### Роли хранилищ

Поле `homes` в [DATA-DOMAINS-REGISTRY.yaml](../DATA-DOMAINS-REGISTRY.yaml) использует переносимые ролевые метки вместо имён конкретных репозиториев (имена репозиториев — личный выбор каждого пользователя, не часть шаблона):

| Роль | Назначение | Пример |
|---|---|---|
| `governance-personal` | Планирование, рабочие контексты, сессионные диалоги (2.5/2.6) | личный стратегический репозиторий пользователя |
| `personal-data` | Активный поток событий/телеметрии (2.2), карантин вне оси | отдельный append-only репозиторий или БД |
| `personal-declarative` | Устойчивые факты о пользователе (2.1) | Pack с личными данными |
| `promoted-knowledge` | Оформленное, промотированное знание (2.3) | Pack-репозитории предметной области |
| `platform-runtime` | Вычисляемые/агрегированные представления вне git | платформенная БД (для дистрибутива — опционально) |

### Машиночитаемый источник истины

Полная схема (12 доменов, темп, уровень чувствительности, разрешённые потоки, механизм контроля, зрелость) — в [DATA-DOMAINS-REGISTRY.yaml](../DATA-DOMAINS-REGISTRY.yaml). Эта таблица — сжатое человекочитаемое резюме, YAML остаётся источником истины при расхождении.

## Что не входит в это решение

- Миграция существующей структуры конкретного пользователя к этой карте — личное решение каждого пользователя, не требование шаблона.
- Механизм технического контроля доступа для карантина (2.4/2.6) — декларируется как необходимость, реализация вне рамок этого ADR.
- Правки в [DATA-RESIDENCY.md](../DATA-RESIDENCY.md) — документ отдельного, уже закрытого решения (WP-475); не редактируется.
